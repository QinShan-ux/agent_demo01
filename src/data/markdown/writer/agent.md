### RAG知识库构建和向量化

背景：RAG可能是各种文档，例如pdf，word或者只是一个txt文本
RAG准确召回的准确性主要取决于两个方面
- 怎么存（索引策略）：决定了你的知识以什么结构、什么粒度、什么形式被组织起来。存得不好，查的时候神仙难救。
- 怎么查（检索策略）：决定了用户的问题如何与知识库匹配。查得不好，知识再多也找不到。

#### 📦 怎么存（索引策略）—— 让知识“有序可循”
##### 1.切分策略
这是最基础的一步，决定了你的知识片段是“精准的子弹”还是“散弹”。

- 按语义边界切分：按段落、句子结束符来切，而不是机械地按字符数切。用 RecursiveCharacterTextSplitter 并设置好 separators=["\n\n", "\n", "。", "！", "？"]，能有效避免把连贯的语义切碎。

- 子父文档结构：入库时，子块（小）用于检索，父块（大）用于回答。这样可以先用小块精准命中，再返回完整上下文。

##### 2.元数据与父子结构（Metadata & Parent Document）
这是“存”环节最重要的手段。
- 打标签：给文档附上元数据（如文档类型、部门、时间、作者）。检索时，先用元数据筛选，再语义搜索，相当于加了一道前置过滤。

- 建立父子关系：子块负责检索，父块（完整段落/章节）负责为 LLM 提供上下文。

##### 3.多层索引（Multi-level Indexing）
如果知识库很大且结构丰富，可以构建不同粒度的索引。
- 摘要索引：为每个文档生成摘要并建立索引，先搜摘要，再查详情。

- 关键词索引：单独提取重要的人名、地名、产品名建立关键词索引，作为辅助。

#### 🔍 怎么查（检索策略）—— 让问题“精确命中”
“查”的目标是：无论用户提问多口语化、多模糊，都能准确映射到文档中的相关片段。<br/>
##### 1.查询理解（Query Understanding）
用户的问题往往是模糊的，需要先“翻译”成检索语言。
- 查询改写：用 LLM 将口语化问题改写成更正式、更接近文档语言的查询语句。
- HyDE：先让 LLM 生成一个“假设性答案”，再用答案去检索（已在上一轮讨论过）。
##### 2.多路召回（Multi-query Retrieval）
从不同维度去查，再合并结果，避免遗漏。
- BM25 + 向量检索：结合关键词匹配和语义匹配，是最经典的组合。
- 多角度查询：对用户问题生成 3-5 个变体，分别检索，合并去重。
##### 3.重排序（Reranking）
先粗召回（Top-20），再精排序（Top-5）。用轻量级但精准的模型进行二次排序，确保交给 LLM 的是最相关的片段。
##### 4.检索后策略（Post-retrieval Strategies）
这是最容易被忽视，但又极有效的一环。它不改变召回结果，但能显著提升最终答案质量。
- Lost-in-the-Middle 规避：大模型对中间位置的关注度最低。在拼 Prompt 时，可以把最关键的片段放在开头（System Prompt 附近）和结尾（问题的正上方）。
- 上下文压缩：如 LLMLingua，在保留关键信息的前提下，将冗余内容压缩掉。
- 检索后过滤：如果重排序后，相关性分数依然都很低（如低于某个阈值），就放弃检索结果，直接告诉用户“知识库中没有相关信息”，避免模型强行编造（幻觉）。
#### 🎯 快速诊断：你的问题出在哪一端？
如果召回不准，你可以用一个简单的问题来判断：
```text
在召回的结果中，前 3 名有没有包含正确答案？
```
- 如果“有”：那说明“存”和“查”都做对了，问题出在“检索后策略”，即：答案被召回了，但在 Prompt 里的位置不好，或者被别的片段干扰了。解决方法是优化 Prompt 结构。
- 如果“没有”：那问题在“存”或“查”本身。可以继续检查：
  - “存”的问题：答案可能在文档里，但切分时被断开了，或者根本没有被向量化索引。解决方法是优化切片粒度，并检查 Embedding 模型。
  - “查”的问题：向量检索没能把相关文档的语义匹配上。解决方法是引入混合检索（BM25 + 向量），或优化查询改写。
#### 💎 总结
```text
“存”决定了你的知识能被“找”到的上限，而“查”决定了你能接近这个上限的程度。
```
- 存储层（离线）：建立混合索引（向量 + 关键词）并维护好元数据。
- 查询层（在线）：执行查询理解 → 混合检索 → 重排序 → 检索后处理这一标准流水线。
